## Safety gate

```cpp
constexpr bool kGazelleDeferredStockResearchEnabled = false;
```

The **existing initial OpenStream still calls the stock codec factory synchronously**. The staged worker path exists only for an *already-started video worker stream-change* and is never selected with the switch OFF. Even if someone deliberately changes the switch in a future research build, the helper calls only `CDVDFactoryCodec::CreateVideoCodec` with fallback; it contains **no actual libdovi first-AU call or research OMX alias selection**. It is **not** safe to switch ON: no real first RPU, no parallel BL/EL decoder, no Dolby FEL residual reconstruction, no registry-native OMX component, no proven rollback.

Source-only tests (from a full checkout):

```sh

```

These tests **do not compile Kodi** and do not prove Android thread correctness. They inspect source structure and fail closed if the disabled feature changes, the timeout or first-packet ordering guard disappears, source references to a research alias are introduced or stock creation is removed. Their expected final line includes `target_compile=NOT_TESTED on_device=NOT_TESTED`.

## 24 October 2026 — genuine FEL/MEL RPU classification through Annex B AND hvcC (host CI PASS)

The read-only, production-linked `xbmc/utils/GazelleFELPrecreateProbe.h` previously accepted **only** hvcC length-prefixed HEVC packets. That assumed an in-band packet had a 23+ byte `hvcC` record and a known NAL length width, which is **not guaranteed for Blu-ray MPEG-TS Annex B**. Valid metadata could therefore fail closed as `Unknown` *before* libdovi was called. No actual disc packet has been collected to confirm its exact framing, so neither transport is assumed universally.

[Research commit 0af68525](https://github.com/angelcode1/xbmc/commit/0af685254f9b66d2a52d88221d1d23d0806afb54) adds a separate **read-only Annex B** branch for strictly leading `00 00 01` and `00 00 00 01` start codes (including mixed lengths) without requiring an hvcC record. When the AU does **not** begin with an Annex B start code, the original trusted `hvcC` length-width requirement remains. One shared bounded NAL validator rejects forbidden bits, temporal ID zero, truncated NALs, more than 512 NALs, more than one RPU, RPU over 64 KiB, AU over 16 MiB, protection, or missing BL/EL. It has no heap allocations, NAL rewriting, decoder selection or packet ownership change.

`tests/TestGazelleFELPrecreateProbe.cpp` now checks synthetic Annex B FEL and MEL framing and malformed/ambiguous cases using the clearly labelled **fake FFI**. [Host run 40069287963](https://github.com/angelcode1/xbmc/actions/runs/40069287963) completed SUCCESS with the new tests. `tests/TestGazelleFELAuthenticRpu.cpp` additionally feeds the **same hash-pinned upstream real FEL and MEL RPUs** through both hvcC length-prefixed and mixed-start-code Annex B transport. This calls the real **libdovi 3.3.2** library for each path, including the protected and duplicate-RPU fallback checks. ## 24 October 2026 — CRITICAL priority-10 codec retry can overtake priority-1 flush (dual-epoch NO-GO)

Further exact Kodi worker source tracing found **two** retry branches, `CDVDVideoCodec::VC_FLUSHED` and `CDVDVideoCodec::VC_REOPEN`, in `VideoPlayerVideo.cpp` that requeue the **original** `CDVDMsgDemuxerPacket` using `SendMessage(msg, 10)`. The same worker receives seek/flush via `CDVDMsg::GENERAL_FLUSH` at **priority 1**. The actual `CDVDMessageQueue::Put/Get` order therefore allows a queued **priority-10 old BL retry to overtake a previously queued priority-1 seek flush**. A previous, simpler test showed priority-1 flush overtakes priority-0 normal packets; **both** reorderings can occur. Worker epoch updated only upon actually processing the flush is therefore unsafe even if every message has a valid single-assignment producer stamp.

[Regression commit 4ff18c45](https://github.com/angelcode1/xbmc/commit/4ff18c4561cc7863449d61ef83172c3714a876ed) extends the **actual Kodi queue/message/header plus Kodi-typed bridge host link** (`tests/TestGazelleKodiTypedBridgeLinkedHost.py`). It produces an original epoch-1 BL, dequeues it once, publishes/enqueues epoch-2 flush (priority 1), re-enqueues that *same* original as priority 10 (the decoder retry's real priority), and verifies Kodi **gets the old epoch-1 packet before its flush**. It also verifies the original owner is destroyed **once**, its immutable original producer stamp stays 1, priority-10 does not double-account ordinary bytes, and the priority-1 flush follows. [CI 40083455974](https://github.com/angelcode1/xbmc/actions/runs/40083455974) both jobs passed; an intermediate first test failed only because Kodi `Get(..., int& priority)` uses that parameter as a **minimum requested priority** as well as output: the test must reset it to 0 between dequeues.

[Dual-epoch policy `GazelleFELPrecreateAdmission.h` 5fa61bc6](https://github.com/angelcode1/xbmc/commit/5fa61bc6b59a02e9d06285dbe38df5c36f3f3745) is a **pure, UNWIRED compile-time guard**, not a queue patch or native FEL implementation. `ClassifyEpoch(packetEpoch, publishedProducerEpoch, appliedWorkerFlushEpoch)` returns one of `UntaggedStock`, `StaleReject`, `AwaitBarrier`, `InvalidReject`, or `MetadataOnly`. It rejects epoch-1 high-priority retry if epoch 2 has been producer-published **even when worker flush is still epoch 1**, and refuses epoch-2 metadata pairing **until** the worker has actually applied epoch-2 flush. `MayDirectStockReplay` likewise refuses old-epoch timeout stock fallback after producer seek publication. `MetadataOnly` means *potential owner pairing*, not FEL, codec choice or valid combined AU.

[Host CI 40083739512](https://github.com/angelcode1/xbmc/actions/runs/40083739512) **both source-only and real-libdovi jobs SUCCESS**; actual-linked Kodi typed bridge printed `GAZELLE_KODI_TYPED_BRIDGE_LINK_HOST_PASS retry_priority_10_overtakes_flush_1=true ... dual_epoch_admission_rejects_stale_and_premature_new=true` in both normal C++17 and UBSan. The source checker was extended to **22 negative mutations** and now requires both Kodi priority-10 retry sites, so the ordering hazard remains visible to future edits.

**NOT SOLVED FOR LIVE KODI:** the producer-published epoch and worker-applied barrier epoch are **not currently exposed as a synchronized pair to the live worker**; no real producer lock covers both BL/EL and all seek/reset/stream-change/close sources; and an `AwaitBarrier` new-epoch packet needs a bounded, lossless hold/retry decision **without** `PutBack` reordering or stock decode before flush. Sampling two epoch counters without correct locking could still race the publisher. A held old BL must be revoked before any timeout stock handoff if the seek is published, not merely when its flush is dequeued. Those proofs and real Kodi worker lifecycle integration are prerequisites to removing the hard `kDeferredStockResearchEnabled=false` guard. The policy remains completely **unwired**, no original packet moved into a live new owner gate; no full Kodi runtime, APK or Cube tests, no native FEL residual reconstruction and no R0 rollback.

## 24 October 2026 — two-original AwaitBarrier host gate PASS, backpressure still UNWIRED

[Isolated `GazelleFELAwaitBarrierOwners.h` commit 4f86f191](https://github.com/angelcode1/xbmc/commit/4f86f191853edb630eaf72657b922fbee8a6a0ab) adds a **non-deployable, thread-external**, fixed-size original-message ownership contract for Kodi's priority-10 retry versus priority-1 seek-flush inversion. Previously, pure `ClassifyEpoch` correctly returned `AwaitBarrier` when the producer had published epoch N but the worker had not yet applied N; it did not prescribe lossless bounded retention. The new model takes the original `std::shared_ptr<Message>` only if its `ClassifyEpoch(packet,published,applied)==AwaitBarrier`, declared payload bytes are nonzero and <=16MiB/layer, and the holder has room. At most **TWO original messages, 32MiB total declared bytes, and one pending generation** can be held. No packet payload, crypto state, DTS/PTS or underlying `DemuxPacket*` is copied, modified or reallocated.

Its `TryHold(Owner& ...)` **does not consume** a third/oversized/invalid/stale/deadline-overrun message: `CallerMustRetain` makes the missing **upstream backpressure** obligation explicit. There is NO safe implicit drop or stock replay. Abstract monotonic `nowTicks` and `maxWaitTicks` signal `DeadlineNeedsControlRecovery` but keep all held originals; this is **not a validated wall-clock timeout or Kodi scheduling parameter**. `TakeAfterBarrier(published,applied,nowTicks)` only returns the same original owners in input order once `published==applied==originalEpoch`; it returns no messages before applied flush, even after timeout. `DropSuperseded` explicitly releases stale held originals on newer producer seek, while `Close()` permanently refuses new retention until a fresh gate instance is constructed. This is a strict offline ownership design, **not** a live queue backpressure or full seek/flush algorithm.
